Room 1: Introduction

What Microsoft Sentinel is and how it fits into the role of a Security Operations Analyst.

Key Concepts

  • SIEM: collects and correlates logs from across the environment.
  • SOAR: automates response through playbooks and automation rules.
  • Built on a Log Analytics workspace and queried with KQL.
  • Cloud native: no servers to build, scales with data volume.
SIEM SOAR

Core Building Blocks

  • Data connectors: bring logs in.
  • Analytics rules: detect threats.
  • Incidents: group related alerts for triage.
  • Workbooks: dashboards and visualizations.
  • Hunting: proactive KQL searches.
  • Playbooks: automated response with Logic Apps.
Components

The SOC Analyst's Role

A Security Operations Analyst uses Sentinel daily to triage incidents, investigate alerts, hunt for threats that rules missed, tune noisy detections, and run or build automated responses. Sentinel becomes the central console where every security signal is reviewed.

Room 2: Deploy

Everything needed for the initial Microsoft Sentinel deployment.

Deployment Steps

How To

  1. Create a resource group in the Azure portal.
  2. Create a Log Analytics workspace in that resource group and region.
  3. Search for Microsoft Sentinel, select Create, and add it to the workspace.
  4. Set data retention on the workspace.
  5. Install solutions from Content hub.

Planning Considerations

  • Workspace design: one central workspace is simplest unless data residency or separation rules require more.
  • Region: place the workspace where compliance requirements allow.
  • Cost: billing is based on data ingested and retained, so plan which logs matter most.
  • Retention: balance investigation needs against storage cost.

Room 3: Ingest Data

No logs, no correlation, no analysis, no action. This room covers getting log data into Sentinel.

Connect a Data Source

How To

  1. Open Content hub and install the solution for your source.
  2. Go to Data connectors and open the connector.
  3. Follow the connector's configuration steps.
  4. For VMs, install the Azure Monitor Agent and create a Data Collection Rule.
  5. For firewalls and appliances, forward Syslog or CEF through a Linux log forwarder.

Room 4: Detect

How Sentinel detects threats and turns them into actionable incidents.

Analytics Rule Types

  • Scheduled: KQL runs on a set interval.
  • Near Real Time (NRT): runs about every minute.
  • Microsoft Security: creates incidents from Defender alerts.
  • Fusion: machine learning for multistage attacks.
  • Anomaly: flags unusual behavior.
  • Threat Intelligence: matches logs to known indicators.
Rule Types

Create a Scheduled Rule

How To

  1. Go to Analytics → Create → Scheduled query rule.
  2. Name it, set severity, and map MITRE ATT&CK tactics.
  3. Paste the KQL and set frequency and lookback.
  4. Map entities: Account, Host, IP.
  5. Enable incident creation and alert grouping.
Analytics Rules MITRE ATT&CK

Example Rule: Password Spray

One IP failing sign ins against many different accounts in a short window.

SigninLogs
| where TimeGenerated > ago(1h)
| where ResultType in ("50126", "50053")
| summarize Accounts = dcount(UserPrincipalName),
            Attempts = count()
    by IPAddress
| where Accounts > 10
| project IPAddress, Accounts, Attempts

Investigation Steps

How To

  1. Open the incident and assign an owner.
  2. Review alerts, evidence, and mapped entities.
  3. Use the investigation graph to pivot between users, hosts, and IPs.
  4. Run follow up KQL in Logs to scope the activity.
  5. Close as True Positive, Benign Positive, or False Positive.
Investigation Graph

Automation Rules vs Playbooks

  • Automation rules: lightweight actions such as assigning owners, changing severity, tagging, or closing known benign incidents.
  • Playbooks: Logic Apps for complex response, such as disabling a user, isolating a device, or posting to Teams.
  • Automation rules can trigger playbooks.
Logic Apps SOAR

Pivot Query: Everything a Suspicious IP Did

let badIP = "203.0.113.45";
union isfuzzy=true SigninLogs, AzureActivity, OfficeActivity
| where TimeGenerated > ago(7d)
| where IPAddress == badIP or CallerIpAddress == badIP or ClientIP == badIP
| project TimeGenerated, Type, UserPrincipalName, Caller, OperationName
| sort by TimeGenerated asc
